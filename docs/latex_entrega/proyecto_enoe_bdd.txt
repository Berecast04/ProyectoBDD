\section{Resumen}

Este proyecto construye y compara dos formas de almacenar y consultar datos
históricos de la Encuesta Nacional de Ocupación y Empleo (ENOE): una base de
datos centralizada y una base de datos distribuida en dos computadoras. La
fuente utilizada fue el portal oficial del Instituto Nacional de Estadística y
Geografía (INEGI), con información del periodo 2015--2024.

El proceso completo incluyó descarga de archivos, extracción de ZIP, lectura de
DBF, transformación a Parquet, diseño centralizado normalizado, carga en
PostgreSQL, fragmentación horizontal por entidad federativa, restauración de un
nodo en una segunda máquina, configuración de \texttt{postgres\_fdw},
consultas distribuidas, validación y respaldos.

La comparación de diez consultas mostró que la base centralizada fue más rápida
en seis casos y la distribuida en cuatro. La conclusión no es que una
arquitectura sea siempre superior: la centralizada resultó más conveniente
para consultas globales simples, mientras que la distribuida obtuvo ventajas
cuando la consulta coincidió con la fragmentación o cada nodo realizó una
agregación parcial antes de enviar su resultado.

\section{Requisitos de la práctica}

La práctica solicitó los siguientes elementos:

\begin{enumerate}[label=\arabic*.]
  \item Fuente real: ENOE, población de 15 años y más, con histórico superior a cinco años.
  \item Diseño centralizado OLTP normalizado hasta tercera forma normal y modelo entidad--relación.
  \item Al menos cinco consultas centralizadas.
  \item Análisis para transformar el sistema en una base distribuida.
  \item Diseño de la distribución.
  \item Distribución o fragmentación de los datos.
  \item Modificación de cinco consultas centralizadas para obtener versiones distribuidas equivalentes.
  \item Al menos cinco consultas distribuidas nuevas.
  \item Validación de la base distribuida contra la base centralizada.
  \item Entrega del trabajo escrito, scripts y por lo menos tres respaldos: centralizado y dos nodos.
\end{enumerate}

Todos estos puntos se cubren en las secciones siguientes.

\section{Conceptos básicos para una persona sin experiencia}

\subsection{¿Qué es una base de datos?}

Una base de datos es un conjunto organizado de información. PostgreSQL es el
programa que almacena esa información y permite consultarla mediante SQL. SQL
es el lenguaje usado para pedir datos, por ejemplo contar registros o agrupar
personas por entidad federativa.

\subsection{Base centralizada}

En una base centralizada todos los datos se encuentran en un solo servidor. En
este proyecto esa base se llama \texttt{enoe\_centralizada}. Su ventaja es la
simplicidad: una sola computadora administra toda la información. Su
desventaja es que el almacenamiento y procesamiento se concentran en un único
equipo.

\subsection{Base distribuida}

En una base distribuida los datos se reparten entre varias computadoras. Para
este proyecto, las entidades 1 a 16 se almacenaron en el nodo 1 y las entidades
17 a 32 en el nodo 2. Un coordinador permite consultar ambos nodos desde un
solo punto.

\subsection{Fragmentación horizontal}

Fragmentar horizontalmente significa dividir las filas de una tabla usando una
regla. La tabla conserva las mismas columnas, pero cada nodo guarda filas
diferentes:

\begin{center}
\begin{tabular}{lll}
\toprule
\textbf{Nodo} & \textbf{Regla} & \textbf{Ubicación}\\
\midrule
Nodo 1 & \texttt{id\_entidad} entre 1 y 16 & Máquina principal\\
Nodo 2 & \texttt{id\_entidad} entre 17 y 32 & Máquina remota\\
\bottomrule
\end{tabular}
\end{center}

\subsection{Coordinador y tablas foráneas}

La extensión \texttt{postgres\_fdw} permite crear tablas foráneas. Una tabla
foránea parece local, pero sus datos se encuentran en otro PostgreSQL. En este
proyecto, \texttt{fact\_ocupacion\_nodo\_2} apunta a la computadora del segundo
nodo.

\section{Requerimientos de instalación}

\subsection{Equipo recomendado}

\begin{itemize}
  \item Dos computadoras con Windows 10 u 11 de 64 bits.
  \item Al menos 8 GB de memoria RAM; 16 GB es recomendable.
  \item Al menos 30 GB libres para datos, bases y respaldos.
  \item Ambas computadoras conectadas a la misma red local.
  \item Evitar suspensión, cambio de red o VPN durante consultas y respaldos.
\end{itemize}

\subsection{Programas para la máquina principal}

\begin{itemize}
  \item Python 3.12 o compatible.
  \item PostgreSQL 17.
  \item pgAdmin 4.
  \item Visual Studio Code o Cursor, opcional pero recomendado.
  \item Git, opcional si el proyecto se transfiere como carpeta.
  \item MiKTeX o TeX Live para compilar esta documentación.
\end{itemize}

\subsection{Programas para la máquina del nodo 2}

\begin{itemize}

\subsection{Configuración de variables}

El archivo \ruta{.env} guarda valores que cambian entre computadoras, como el
usuario, la contraseña y los nombres de las bases. El proyecto incluye
\ruta{.env.example}, que funciona como plantilla y no contiene credenciales
reales.

En PowerShell, desde la raíz del proyecto, crear la copia:

\begin{lstlisting}[language=bash]
Copy-Item .env.example .env
\end{lstlisting}

Después abrir \ruta{.env} con un editor de texto y configurar:

\begin{lstlisting}[language=bash]
DB_USER=postgres
DB_PASSWORD=CAMBIAR_POR_PASSWORD_LOCAL
DB_HOST=localhost
DB_PORT=5432
DB_CENTRAL=enoe_centralizada
DB_NODE_1=enoe_nodo_1
DB_NODE_2=enoe_nodo_2
DB_COORDINATOR=enoe_coordinador
START_YEAR=2015
END_YEAR=2024
\end{lstlisting}

\begin{itemize}
  \item \texttt{DB\_USER}: usuario de PostgreSQL; normalmente es
        \texttt{postgres}.
  \item \texttt{DB\_PASSWORD}: contraseña elegida durante la instalación de
        PostgreSQL en esa computadora.
  \item \texttt{DB\_HOST}: se deja como \texttt{localhost} para las bases
        locales.
  \item \texttt{DB\_PORT}: PostgreSQL usa normalmente el puerto \texttt{5432}.
  \item \texttt{DB\_CENTRAL}, \texttt{DB\_NODE\_1},
        \texttt{DB\_NODE\_2} y \texttt{DB\_COORDINATOR}: nombres de las bases
        utilizadas por los scripts.
  \item \texttt{START\_YEAR} y \texttt{END\_YEAR}: periodo histórico a
        procesar.
\end{itemize}

\textbf{Ejemplo:} si la persona eligió una contraseña propia al instalar
PostgreSQL, debe escribirla únicamente en su archivo local:

\begin{lstlisting}[language=bash]
DB_PASSWORD=CONTRASENA_ELEGIDA_POR_EL_USUARIO
\end{lstlisting}

El archivo \ruta{.env} está incluido en \ruta{.gitignore}; por lo tanto, no se
sube a GitHub. Solo se publica \ruta{.env.example}, que conserva marcadores de
ejemplo. Tampoco deben colocarse contraseñas reales en capturas, documentos,
scripts SQL o mensajes compartidos.

\subsection{Credenciales del coordinador distribuido}

El script \ruta{sql/distribuido/coordinador/01_fdw_config.sql} contiene estos
marcadores:

\begin{lstlisting}
OPTIONS (host 'IP_NODO_2', dbname 'enoe_nodo_2', port '5432');
OPTIONS (user 'postgres', password 'PASSWORD_NODO_1');
OPTIONS (user 'postgres', password 'PASSWORD_NODO_2');
\end{lstlisting}

Antes de ejecutarlo, cada equipo debe sustituir los marcadores en su copia
local. No se debe guardar ni publicar el script con contraseñas reales. Una vez
creado el \texttt{USER MAPPING}, PostgreSQL almacena internamente la información
necesaria para la conexión.

\section{Diseño centralizado}

\subsection{Modelo}

La base \texttt{enoe\_centralizada} usa una tabla de hechos
\texttt{fact\_ocupacion} y dimensiones para tiempo, entidad, municipio, sexo,
edad, nivel educativo, condición de ocupación, sector y posición laboral.

\begin{center}
\small
\begin{tabularx}{\textwidth}{lX}
\toprule
\textbf{Tabla} & \textbf{Propósito}\\
\midrule
\texttt{dim\_tiempo} & Año y trimestre.\\
\texttt{dim\_entidad} & Entidades federativas.\\
\texttt{dim\_municipio} & Municipios.\\
\texttt{dim\_sexo} & Catálogo de sexo.\\
\texttt{dim\_edad} & Edad o grupo de edad.\\
\texttt{dim\_nivel\_educativo} & Nivel de estudios.\\
\texttt{dim\_condicion\_ocupacion} & Condición laboral.\\
\texttt{dim\_sector\_actividad} & Sector económico.\\
\texttt{dim\_posicion\_ocupacion} & Posición en la ocupación.\\
\texttt{fact\_ocupacion} & Llaves foráneas y métricas: factor, horas e ingreso.\\
\bottomrule
\end{tabularx}
\end{center}

La separación de catálogos evita repetir descripciones en millones de filas.
Cada dimensión tiene una llave primaria y la tabla de hechos contiene llaves
foráneas, lo que permite justificar la tercera forma normal.

\section{Vista global y problema de rendimiento}

La primera estrategia creó una vista global:

\begin{lstlisting}
CREATE VIEW vw_fact_ocupacion_global AS
SELECT *, 1 AS nodo_origen FROM fact_ocupacion_nodo_1
UNION ALL
SELECT *, 2 AS nodo_origen FROM fact_ocupacion_nodo_2;
\end{lstlisting}

La vista es correcta desde el punto de vista lógico, pero una consulta global
puede obligar al coordinador a procesar o transferir millones de filas antes de
agruparlas. La evidencia registró una consulta de aproximadamente 13 minutos.

\evidencia{evidencia_042.png}{Consulta global del coordinador con tiempo elevado.}

La solución fue mantener el coordinador, pero consultar cada tabla foránea con
agregaciones parciales. Así, cada nodo procesa sus datos y el coordinador recibe
solamente pocas filas.

\section{Metodología de comparación de rendimiento}

Se compararon diez pares de consultas equivalentes. Cada consulta se ejecutó
tres veces:

\begin{enumerate}
  \item La primera ejecución se consideró calentamiento de caché.
  \item Se registraron las ejecuciones 2 y 3.
  \item Se calculó su promedio.
  \item Se confirmó que centralizada y distribuida devolvieran resultados equivalentes.
\end{enumerate}

Los valores mostrados por pgAdmin tienen formato
\texttt{hh:mm:ss.sss}; por ello, los resultados de la tabla se expresan en
\textbf{segundos}, no en milisegundos.

La mejora distribuida se calculó como:

\[
\text{Mejora} =
\frac{T_{\text{central}}-T_{\text{distribuido}}}
{T_{\text{central}}}\times 100.
\]

Un porcentaje positivo favorece a la base distribuida; uno negativo favorece a
la centralizada.

\section{Interpretación}

\subsection{Cuándo fue mejor la centralizada}

La centralizada destacó en el conteo global, conteos generales, condición de
ocupación y promedio de horas. Estas operaciones requieren recorrer gran parte
de los datos y la base centralizada evita la latencia de red y la coordinación
entre dos servidores.

La consulta 8 fue especialmente desfavorable para la distribuida. Calcular un
promedio global correctamente requiere que cada nodo produzca suma y cantidad,
y que el coordinador combine ambos valores. El costo de los escaneos remotos y
la red superó el beneficio del paralelismo.

\subsection{Cuándo fue mejor la distribuida}

La distribuida ganó en consultas 2, 5, 7 y 9. La mayor ventaja apareció en la
consulta 9, con 77.76\% de mejora. Cada nodo filtró 2024, agrupó sus propias
entidades y devolvió solamente tres filas. Este patrón aprovecha correctamente
la distribución: el procesamiento se acerca a los datos y se reduce la
transferencia.

La consulta 10 accedió únicamente al nodo 2 porque las entidades 17 y 18
pertenecen a ese fragmento. Aunque el tiempo fue ligeramente mayor que el
centralizado, la diferencia fue pequeña. La latencia de la red local explica
que una consulta remota corta no necesariamente sea más rápida, aun cuando
acceda al nodo correcto.

\section{Conclusión}

Con base en las diez pruebas, la base centralizada es la opción más conveniente
si el sistema se ejecutará en una sola computadora y la mayoría de las
consultas necesita recorrer toda la información. En este experimento fue más
rápida en seis de diez consultas y obtuvo un promedio global 7.2\% menor.
También es más sencilla de instalar, respaldar y administrar.

La base distribuida no debe considerarse incorrecta ni inútil. Su principal
ventaja apareció en consultas alineadas con la fragmentación y en agregaciones
parciales. La consulta 9 demostró que puede superar ampliamente a la
centralizada cuando cada nodo procesa localmente y devuelve pocos resultados.
Además, aporta separación física, disponibilidad organizacional y posibilidad
de crecimiento horizontal.

Por lo tanto, la conclusión adecuada es:

\begin{quote}
\textbf{Para el entorno de prueba actual y consultas predominantemente
globales, la base centralizada ofrece el mejor rendimiento promedio y menor
complejidad. La base distribuida es preferible cuando las consultas son
regionales, coinciden con el criterio de fragmentación o el volumen futuro
requiere repartir almacenamiento y procesamiento entre varios equipos.}
\end{quote}

No existe una arquitectura universalmente mejor. La decisión depende del
patrón real de consultas, la estabilidad de la red, la ubicación de los
usuarios, el crecimiento de los datos y los requisitos de disponibilidad.

Guardar el archivo. Esto permite que PostgreSQL escuche conexiones de red y no
solamente conexiones locales.

\subsubsection{16.2 Configurar \texttt{pg\_hba.conf}}

En el mismo directorio abrir \texttt{pg\_hba.conf} como administrador y
agregar al final una línea con la IP real de la máquina 1:

\begin{lstlisting}
host    enoe_nodo_2    postgres    IP_MAQUINA_1/32    scram-sha-256
\end{lstlisting}

Ejemplo:

\begin{lstlisting}
host    enoe_nodo_2    postgres    10.106.235.149/32    scram-sha-256
\end{lstlisting}

\texttt{/32} autoriza únicamente esa computadora. No se recomienda
\texttt{0.0.0.0/0}, porque permitiría intentos de conexión desde cualquier
dirección.

\subsubsection{16.3 Abrir el Firewall de Windows de forma visual}

\begin{enumerate}
  \item En la máquina 2 abrir \textit{Seguridad de Windows}.
  \item Entrar en \textit{Firewall y protección de red}.
  \item Seleccionar \textit{Configuración avanzada}.
  \item Elegir \textit{Reglas de entrada} y después \textit{Nueva regla}.
  \item Seleccionar \textit{Puerto}.
  \item Marcar \textit{TCP} y escribir \texttt{5432} en
        \textit{Puertos locales específicos}.
  \item Seleccionar \textit{Permitir la conexión}.
  \item Marcar solamente el perfil de red utilizado; normalmente
        \textit{Privado}. Evitar \textit{Público} cuando no sea necesario.
  \item Nombrar la regla \texttt{PostgreSQL 17 TCP 5432} y finalizar.
\end{enumerate}

\subsubsection{16.4 Reiniciar PostgreSQL}

Abrir \textit{Servicios}, localizar \textit{postgresql-x64-17}, hacer clic
derecho y elegir \textit{Reiniciar}. Este paso aplica los cambios de los dos
archivos de configuración.

\subsection{17. Probar la conexión de máquina 1 a máquina 2}

En PowerShell de la máquina 1 sustituir la IP por la dirección actual de la
máquina 2:

\begin{lstlisting}
Test-NetConnection 10.106.235.29 -Port 5432
\end{lstlisting}

El resultado correcto contiene \texttt{TcpTestSucceeded : True}. Después
realizar una prueba directa de PostgreSQL:

\begin{lstlisting}
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" `
  -h 10.106.235.29 -p 5432 -U postgres -d enoe_nodo_2 `
  -c "SELECT current_database(), inet_server_addr(), COUNT(*) FROM fact_ocupacion;"
\end{lstlisting}

La contraseña solicitada es la del usuario \texttt{postgres} de la máquina 2,
no la de la máquina 1. Si aparece el conteo del nodo 2, la consulta está
leyendo físicamente PostgreSQL de la otra computadora.

\subsection{18. Configurar el coordinador con \texttt{postgres\_fdw}}

Antes de ejecutar
\ruta{sql/distribuido/coordinador/01_fdw_config.sql}, crear una copia local
temporal o editarla sin guardar credenciales en Git. Sustituir:

\begin{itemize}
  \item \texttt{IP\_NODO\_2} por la IP actual de la máquina 2.
  \item \texttt{PASSWORD\_NODO\_1} por la contraseña local de máquina 1.
  \item \texttt{PASSWORD\_NODO\_2} por la contraseña PostgreSQL de máquina 2.
\end{itemize}

En pgAdmin de la máquina 1 abrir un \textit{Query Tool} conectado a
\texttt{enoe\_coordinador} y ejecutar, en orden:

\begin{enumerate}
  \item \ruta{sql/distribuido/coordinador/01_fdw_config.sql}
  \item \ruta{sql/distribuido/coordinador/02_foreign_tables.sql}
  \item \ruta{sql/distribuido/coordinador/03_views_globales.sql}
\end{enumerate}

Comprobar los servidores:

\begin{lstlisting}
SELECT srvname, srvoptions
FROM pg_foreign_server
ORDER BY srvname;
\end{lstlisting}

Comprobar el acceso a cada fragmento:

\begin{lstlisting}
SELECT 1 AS nodo, COUNT(*) FROM fact_ocupacion_nodo_1
UNION ALL
SELECT 2 AS nodo, COUNT(*) FROM fact_ocupacion_nodo_2
ORDER BY nodo;
\end{lstlisting}

La segunda fila sólo puede obtenerse si el coordinador logra comunicarse con
el PostgreSQL remoto de la máquina 2.

\subsection{19. Actualizar la conexión cuando cambia la IP}

Si los equipos se desconectan o cambian de red, repetir \texttt{ipconfig}. En
la máquina 2 debe actualizarse la IP autorizada en \texttt{pg\_hba.conf} si
cambió la máquina 1, y después reiniciar PostgreSQL.

Si cambió la IP de la máquina 2, ejecutar en
\texttt{enoe\_coordinador}, desde la máquina 1:

\begin{lstlisting}
ALTER SERVER enoe_nodo_2_srv
OPTIONS (SET host 'IP_NUEVA_MAQUINA_2');
\end{lstlisting}

Verificar el cambio y repetir las pruebas de red:

\begin{lstlisting}
SELECT srvname, srvoptions
FROM pg_foreign_server
WHERE srvname = 'enoe_nodo_2_srv';
\end{lstlisting}

\begin{lstlisting}
Test-NetConnection IP_NUEVA_MAQUINA_2 -Port 5432
\end{lstlisting}

\subsection{20. Ejecutar las diez consultas comparativas}

En pgAdmin de la máquina 1:

\begin{enumerate}
  \item Seleccionar \texttt{enoe\_centralizada}, abrir \textit{Query Tool} y
        cargar
        \ruta{sql/comparacion/01_consultas_centralizadas.sql}.
  \item Seleccionar únicamente una consulta completa, desde
        \texttt{EXPLAIN} hasta su punto y coma, y ejecutarla.
  \item Registrar el \texttt{Execution Time} mostrado al final del plan.
  \item Ejecutar la misma consulta tres veces. La primera ejecución sirve para
        calentar caché; se recomienda comparar el promedio de la segunda y
        tercera.
  \item Seleccionar \texttt{enoe\_coordinador}, abrir otro
        \textit{Query Tool} y cargar
        \ruta{sql/comparacion/02_consultas_distribuidas.sql}.
  \item Ejecutar la consulta equivalente, también tres veces y en las mismas
        condiciones.
\end{enumerate}

No debe ejecutarse el archivo completo en un solo bloque, porque varias
consultas recorren millones de filas y la medición dejaría de representar una
prueba individual. Las consultas distribuidas deben agregar primero dentro de
cada nodo y combinar después resultados pequeños; consultar toda la vista
global antes de agrupar transfiere demasiadas filas por red y explica los
tiempos de 13 o 17 minutos observados al inicio.

\subsection{21. Validar equivalencia centralizada y distribuida}

Con ambas máquinas conectadas y el coordinador funcionando, ejecutar:

\begin{lstlisting}
python src/validate_distribution.py
\end{lstlisting}

El script compara conteo total, conteo por año, conteo por entidad y suma del
factor de expansión. Genera
\ruta{docs/resultados_validacion.md}. Cada comprobación debe mostrar
\texttt{OK}. También puede verificarse manualmente que:

\begin{lstlisting}
SELECT
  (SELECT COUNT(*) FROM fact_ocupacion_nodo_1) AS total_nodo_1,
  (SELECT COUNT(*) FROM fact_ocupacion_nodo_2) AS total_nodo_2,
  (SELECT COUNT(*) FROM fact_ocupacion_nodo_1) +
  (SELECT COUNT(*) FROM fact_ocupacion_nodo_2) AS total_distribuido;
\end{lstlisting}

El total distribuido esperado es \texttt{15,645,061}, igual que la base
centralizada.

\subsection{22. Crear los respaldos finales}

Crear las carpetas en la máquina 1:

\begin{lstlisting}
New-Item -ItemType Directory -Force D:\BBD\backups\centralizada
New-Item -ItemType Directory -Force D:\BBD\backups\nodo_1
New-Item -ItemType Directory -Force D:\BBD\backups\coordinador
\end{lstlisting}

Respaldar cada base local:

\begin{lstlisting}
& "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" `
 -U postgres -h 127.0.0.1 -p 5432 -F c -b -v `
 -f "D:\BBD\backups\centralizada\enoe_centralizada.backup" `
 enoe_centralizada

& "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" `
 -U postgres -h 127.0.0.1 -p 5432 -F c -b -v `
 -f "D:\BBD\backups\nodo_1\enoe_nodo_1.backup" `
 enoe_nodo_1

& "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" `
 -U postgres -h 127.0.0.1 -p 5432 -F c -b -v `
 -f "D:\BBD\backups\coordinador\enoe_coordinador.backup" `
 enoe_coordinador
\end{lstlisting}

El respaldo definitivo de \texttt{enoe\_nodo\_2} se recomienda ejecutarlo
localmente en la máquina 2. Así no depende de que una transferencia de varios
millones de registros permanezca estable:

\begin{lstlisting}
& "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" `
 -U postgres -h 127.0.0.1 -p 5432 -F c -b -v `
 -f "C:\BBD\backups\enoe_nodo_2.backup" `
 enoe_nodo_2
\end{lstlisting}

La entrega requiere al menos tres respaldos: centralizada y dos distribuidos.
Se conservan además el coordinador y sus scripts para reproducir toda la
arquitectura. Verificar que cada archivo exista, tenga un tamaño mayor que
cero y que \texttt{pg\_dump} finalice sin error.

\subsection{23. Restaurar un respaldo para comprobarlo}

Para una prueba de restauración se crea una base vacía con otro nombre:

\begin{lstlisting}
CREATE DATABASE enoe_nodo_1_prueba_restore;
\end{lstlisting}

Después, desde PowerShell:

\begin{lstlisting}
& "C:\Program Files\PostgreSQL\17\bin\pg_restore.exe" `
 -U postgres -h 127.0.0.1 -p 5432 `
 -d enoe_nodo_1_prueba_restore -v `
 "D:\BBD\backups\nodo_1\enoe_nodo_1.backup"
\end{lstlisting}

Finalmente se compara el conteo con el original. Esta prueba confirma que el
archivo no sólo existe, sino que puede recuperarse.

\subsection{25. Errores frecuentes y diagnóstico rápido}

\begin{longtable}{p{0.31\textwidth}p{0.61\textwidth}}
\toprule
\textbf{Mensaje o síntoma} & \textbf{Qué revisar} \\
\midrule
\texttt{python no se reconoce} &
Reinstalar Python marcando \textit{Add python.exe to PATH} o cerrar y abrir
PowerShell. \\
\texttt{psql} o \texttt{pg\_dump no se reconoce} &
Usar la ruta completa
\ruta{C:/Program Files/PostgreSQL/17/bin/psql.exe}, como en esta guía. \\
\texttt{password authentication failed} &
La red sí llegó al servidor, pero la contraseña no corresponde al usuario
\texttt{postgres} del equipo de destino. \\
\texttt{no hay una línea en pg\_hba.conf} &
Agregar en la máquina 2 la IP actual de la máquina 1 con \texttt{/32} y
reiniciar PostgreSQL. \\
\texttt{Connection timed out} &
Revisar que ambos equipos estén en la misma red, la IP actual, el servicio,
\texttt{listen\_addresses}, el Firewall y
\texttt{Test-NetConnection}. \\
\texttt{DestinationHostUnreachable} &
La IP no es alcanzable desde la red actual. Confirmar \texttt{ipconfig} en
ambos equipos y desactivar temporalmente VPN o adaptadores que interfieran. \\
\texttt{secuencia de bytes no válida para UTF8} &
En PowerShell establecer
\texttt{\$env:PGCLIENTENCODING="WIN1252"} para esa sesión o ejecutar la
consulta desde pgAdmin. \\
\texttt{'NoneType' object has no attribute 'query'} en pgAdmin &
Seleccionar únicamente una sentencia SQL completa y volver a ejecutarla. Si
persiste, cerrar y abrir el \textit{Query Tool}; suele ser un problema de la
interfaz, no del servidor. \\
Consulta distribuida excesivamente lenta &
Confirmar la red y usar agregación por nodo antes de \texttt{UNION ALL}.
Evitar transferir la vista global completa para luego agruparla. \\
\texttt{pg\_dump}: el servidor cerró la conexión &
Comprobar que PostgreSQL continúe en ejecución, que el equipo no se suspenda y
crear el respaldo del nodo 2 localmente en la máquina 2. \\
\bottomrule
\end{longtable}

\section{Problemas encontrados y soluciones}

\begin{longtable}{p{0.27\textwidth}p{0.65\textwidth}}
\toprule
\textbf{Problema} & \textbf{Solución}\\
\midrule
\endhead
PostgreSQL remoto no respondía &
Verificar servicio, IP, perfil de red, firewall, \texttt{listen\_addresses} y
\texttt{pg\_hba.conf}.\\
Autenticación fallida &
Usar la contraseña correcta del usuario remoto y actualizar el
\texttt{USER MAPPING}.\\
La IP cambió &
Obtener la nueva IP con \texttt{ipconfig}, actualizar \texttt{pg\_hba.conf} y
el servidor FDW mediante \texttt{ALTER SERVER}.\\
La vista global tardó más de 13 minutos &
Aplicar agregaciones parciales directamente sobre cada tabla foránea y unir
solo resultados pequeños.\\
Backup remoto interrumpido &
Realizar el respaldo localmente en la máquina 2 y transferir el archivo al
terminar.\\
Red escolar aislaba dispositivos &
Usar una red privada o un hotspot común que permita comunicación entre equipos.\\
\bottomrule
\end{longtable}
